# TimingNote

> **시간이 아니라, 장소가 할 일을 알려주는 위치 기반 할 일 관리 서비스**

TimingNote는 사용자가 자연어로 할 일을 입력하면 AI가 **카테고리·장소·시간 조건을 구조화**하고, 사용자의 현재 위치와 이동 방향을 바탕으로 적절한 장소에서 할 일을 추천하거나 알림을 제공하는 모바일 서비스입니다.

예를 들어 `퇴근길에 다이소에서 건전지 사기`라고 입력하면 `다이소`, `쇼핑`, `퇴근 시간대`를 분석합니다. 이후 주변 후보 매장 중 적절한 장소를 선정하여 사용자가 근처에 도착하거나 벗어날 때 알림을 전달합니다.

## 프로젝트 기간

- 개발 기간: **2026.04.20 ~ 2026.05.18**
- 플랫폼: **iOS 중심 Flutter 애플리케이션**
- 프로젝트 구성: **Flutter App / Spring Boot API / FastAPI AI Server / Infrastructure**

## 핵심 가치

기존 할 일 관리 서비스는 사용자가 정해진 시간을 기억하고 알림 시간을 직접 설정해야 합니다. TimingNote는 할 일을 수행하기 좋은 **시간과 장소의 맥락**을 활용해 사용자의 기억 부담을 줄입니다.

- 자연어 한 문장으로 빠르게 할 일 등록
- 특정 매장뿐 아니라 `카페`, `마트`, `약국` 같은 포괄 장소 지원
- 현재 위치와 이동 방향을 반영한 장소 후보 선정
- 장소 진입·이탈 시점에 맞춘 알림
- 주변에서 지금 처리하기 좋은 할 일 추천

## 주요 기능

### 1. 자연어 기반 할 일 등록

사용자가 입력한 자연어 메모에서 AI가 다음 정보를 구조화합니다.

- 할 일 카테고리
- 장소 표현
- 날짜 및 시간
- 반복 요일
- 시간 범위
- 사용자가 작성한 원본 시간 표현

예시:

```text
입력: 매주 월수금 저녁에 헬스장 가기

카테고리: HEALTH
장소: 헬스장
조건 유형: WEEK
요일: MON, WED, FRI
시간: 18:00 ~ 23:00
```

LLM의 자유 형식 응답을 그대로 사용하지 않고 Pydantic 모델과 Structured Output을 적용하여 백엔드가 예측 가능한 형태로 결과를 처리할 수 있도록 구성했습니다.

### 2. 구체 장소와 포괄 장소 분류

할 일에 포함된 장소를 다음 두 유형으로 구분합니다.

- `SPECIFIC`: 스타벅스 강남점, 서울역 등 특정 장소
- `GENERIC`: 카페, 마트, 약국 등 여러 후보가 존재하는 장소

AI는 문장에서 장소 표현을 추출하는 데 집중하고, 최종 장소 유형 판별은 백엔드가 담당합니다.

카카오 장소 검색 결과, 사용자 등록 장소, 장소 카테고리 등을 종합하여 유형을 판단함으로써 AI 응답에 비즈니스 규칙이 종속되지 않도록 구성했습니다.

### 3. 장소 검색 및 후보지 관리

카카오 Local API와 Google Places API를 이용하여 장소를 검색하고 할 일별 후보 장소를 관리합니다.

- 키워드 기반 장소 검색
- 현재 위치 중심 후보 장소 탐색
- 구체 장소 및 포괄 장소 후보 저장
- 장소명·카테고리 유사도 기반 매칭
- 장소 영업시간 관리
- 사용자 지정 장소 별칭 지원

### 4. 위치 기반 Geofence 알림

사용자 주변의 할 일 후보를 분석해 모바일 운영체제에 등록할 Geofence 슬롯을 계산합니다.

후보 우선순위에는 다음 조건이 반영됩니다.

- 현재 위치와 후보 장소 사이의 거리
- 사용자의 이동 방향
- 사용자가 등록한 장소인지 여부
- 할 일의 알림 활성화 여부
- 할 일의 시간 조건

모바일 OS의 지역 모니터링 개수 제한을 고려해 최대 18개 슬롯만 활성화합니다.

하나의 할 일이 슬롯을 독점하지 않도록 할 일당 최대 2개의 장소만 선택합니다.

Geofence 진입·이탈 이벤트가 발생하면 서버가 FCM을 통해 알림을 전송합니다. 앱이 포그라운드 상태일 때는 시스템 알림 대신 인앱 토스트를 표시합니다.

### 5. 실시간 Geofence 슬롯 동기화

서버에서 슬롯 재계산이 완료되면 SSE(Server-Sent Events)를 통해 앱에 변경 사실을 전달합니다.

앱은 새로운 슬롯 정보를 받아 네이티브 Geofence 설정을 갱신합니다.

- SSE heartbeat를 통한 연결 유지 확인
- 앱 생명주기에 따른 연결 관리
- 연결 종료 시 재연결
- 슬롯 변경 이벤트 수신 후 목록 갱신
- 서버와 네이티브 Geofence 상태 동기화

### 6. 현재 위치 기반 할 일 추천

현재 위치를 기준으로 지금 수행할 수 있는 할 일을 조회합니다.

- 설정 반경 내 활성 할 일 조회
- 같은 장소에서 수행할 수 있는 할 일 그룹화
- 가까운 장소순 정렬
- 장소별 할 일 개수 표시
- 지도 마커 및 후보 장소 상세 정보 제공

### 7. 할 일 검색

Elasticsearch를 이용해 할 일 전문 검색을 제공합니다.

- 할 일 내용 및 장소 기반 검색
- 커서 기반 페이지네이션
- 검색 인덱스 초기화
- PostgreSQL 원본 데이터 재색인
- 할 일 변경 시 검색 문서 동기화

### 8. 사용자 장소 및 환경설정

- 집, 회사 등 자주 방문하는 장소 등록
- 사용자 지정 장소 별칭 관리
- 위치·알림 권한 상태 관리
- Geofence 및 알림 사용 여부 설정
- 앱 버전 정보 확인

### 9. 이미지 업로드

클라이언트가 대용량 이미지를 API 서버를 거치지 않고 S3에 직접 업로드할 수 있도록 Presigned URL 방식을 적용했습니다.

- 업로드 URL 발급
- 클라이언트에서 S3로 직접 업로드
- 이미지 처리 완료 콜백
- 다운로드 URL 발급

## 주요 문제 해결

### 1. 모바일 OS의 Geofence 등록 개수 제한

#### 문제

한 사용자가 여러 할 일과 후보 장소를 등록하면 모니터링 대상이 빠르게 증가합니다.

모든 후보를 OS에 등록할 경우 iOS와 Android의 지역 모니터링 제한을 초과할 수 있으며, 단순히 가까운 장소만 고르면 하나의 할 일이 슬롯을 독점할 수 있습니다.

#### 해결

후보 장소마다 다음 기준으로 점수를 계산했습니다.

```text
최종 점수
= 거리 점수 × 0.7
+ 이동 방향 점수 × 0.3
+ 사용자 등록 장소 보너스
```

이후 다음 정책을 적용했습니다.

- 전체 활성 슬롯 최대 18개
- 할 일 하나당 최대 2개 슬롯
- 알림이 비활성화된 할 일 제외
- 현재 위치 기준 실시간 거리를 계산할 수 없는 후보 제외
- 후보군에서 사라진 기존 슬롯 자동 비활성화

이를 통해 OS 제한 안에서 현재 사용자에게 가장 유용한 후보를 동적으로 유지했습니다.

### 2. 슬롯 재계산 요청과 메시지 발행 사이의 데이터 유실 가능성

#### 문제

DB 변경 후 RabbitMQ 메시지를 바로 발행하면 다음과 같은 불일치가 발생할 수 있습니다.

- DB 트랜잭션은 성공했지만 메시지 발행 실패
- 메시지는 발행됐지만 DB 트랜잭션 실패
- 일시적인 메시지 브로커 장애로 이벤트 유실

#### 해결

Transactional Outbox 패턴을 적용했습니다.

1. 재계산 요청을 Outbox 테이블에 저장
2. 스케줄러가 발행 가능한 이벤트를 배치로 조회
3. RabbitMQ 발행 성공 시 `PUBLISHED` 처리
4. 실패 시 지수 백오프로 재시도
5. 최대 재시도 횟수 초과 시 `DLQ` 상태로 전환

외부 장소 API 호출은 DB 트랜잭션 밖에서 수행해 HTTP 응답을 기다리는 동안 커넥션 풀이 점유되지 않도록 분리했습니다.

### 3. 장소 API 호출량과 응답 지연

#### 문제

사용자의 위치가 조금씩 달라질 때마다 동일한 키워드로 외부 장소 API가 반복 호출됐습니다.

캐시 만료 시점에 요청이 집중되면 같은 데이터를 여러 번 조회하는 Cache Stampede 문제도 발생할 수 있었습니다.

#### 해결

Redis 장소 검색 캐시에 다음 정책을 적용했습니다.

- 검색 좌표를 약 1km 단위 grid로 정규화
- 역지오코딩 좌표를 약 30m 단위 grid로 정규화
- 7일 TTL 적용
- TTL에 ±10% jitter를 추가해 동시 만료 분산
- 검색 실패 결과도 저장하는 Negative Caching
- Redis 분산 락을 이용한 Cache Stampede 방지
- 데이터 구조 변경에 대비한 캐시 key versioning
- Redis 장애 시 외부 API를 직접 호출하는 fail-soft 처리
- 민감한 검색어 대신 해시된 key fingerprint 기록

정확도에 큰 영향을 주지 않으면서 외부 API 호출량과 응답 시간을 줄였습니다.

### 4. AI와 백엔드 사이의 책임 경계

#### 문제

초기에는 AI가 장소의 최종 유형과 사용자 장소 별칭까지 판단했습니다.

이 구조에서는 프롬프트 변경이 비즈니스 정책 변경으로 이어지고, 같은 입력도 모델 응답에 따라 서로 다른 유형으로 분류될 수 있었습니다.

#### 해결

역할을 다음과 같이 분리했습니다.

- AI: 원문에서 카테고리·장소 표현·시간 조건 추출
- Backend: 장소 검색, 사용자 별칭 대조, 구체·포괄 장소 판별
- Frontend: 원문 보존 및 분석 결과 수정 UI 제공

AI는 의미 추출에 집중하고, 결정적이어야 하는 장소 정책은 백엔드 규칙으로 관리했습니다.

원문의 할 일 문장을 AI가 의역하지 않도록 응답에서 재작성된 텍스트 필드도 제거했습니다.

### 5. 복합 자연어 시간 조건 구조화

#### 문제

`매주 월수금 저녁과 내일 오전`처럼 반복 조건과 단발 조건이 함께 있는 문장은 하나의 날짜 필드로 표현할 수 없었습니다.

또한 `오후 3시` 같은 단일 시각도 Geofence 활성 구간으로 사용하려면 시작과 종료 시간이 필요했습니다.

#### 해결

시간 조건을 배열로 설계하고 다음 유형을 분리했습니다.

- `DATETIME`
- `DATE`
- `DATE_RANGE`
- `WEEK`
- `TIME_RANGE`

단일 시각은 앞뒤 1시간의 범위로 변환하고, 여러 시간 표현은 각각 독립된 조건으로 저장했습니다.

사용자에게 보여줄 안내 문구는 AI가 다시 생성하지 않고 `rawExpression`을 서버에서 조합해 토큰 사용량과 원문 훼손 가능성을 줄였습니다.

### 6. 서버 슬롯과 앱 Geofence 상태의 동기화

#### 문제

할 일이나 위치가 변경된 뒤 서버의 활성 슬롯만 갱신하면 앱에 등록된 Geofence가 오래된 상태로 남을 수 있었습니다.

반대로 앱이 계속 polling하면 배터리와 서버 자원을 불필요하게 소비합니다.

#### 해결

서버가 슬롯 재계산 완료 이벤트를 SSE로 전달하도록 구성했습니다.

- SSE heartbeat로 연결 유지 확인
- 연결 종료와 일반 API 예외 처리 분리
- 앱 생명주기에 맞춘 재연결
- 변경 이벤트 수신 후 슬롯 목록 재조회
- 네이티브 Geofence 목록과 서버 상태 동기화

### 7. 디바이스 기반 인증 초기화 안정성

#### 문제

최초 실행 중 네트워크 오류가 발생하거나 사용자 설정 생성이 중단되면 디바이스 등록은 되었지만 설정은 없는 부분 초기화 상태가 남을 수 있었습니다.

화면별로 초기화 요청이 겹치면서 중복 API 호출이 발생할 가능성도 있었습니다.

#### 해결

앱 시작 과정을 Bootstrap 서비스로 통합했습니다.

- 디바이스 식별자 생성 및 안전한 저장
- 사용자 등록 또는 기존 사용자 복구
- 기본 사용자 설정 생성 보장
- FCM 토큰 등록
- 초기화 진행 중 중복 요청 차단
- 실패한 단계부터 재시도할 수 있도록 각 단계 멱등성 확보

## 트러블슈팅

### iOS 위치 권한을 요청했지만 백그라운드 감지가 동작하지 않는 문제

#### 원인

`When In Use` 권한만으로는 앱이 백그라운드 상태일 때 Geofence 이벤트 수신이 제한됩니다.

또한 첫 실행부터 `Always` 권한을 요청하면 iOS 권한 흐름이 자연스럽지 않고 사용자의 거절 가능성이 높았습니다.

#### 해결

권한 요청 단계를 다음과 같이 분리했습니다.

1. 기능 설명 후 `When In Use` 요청
2. Geofence 기능 활성화 직전 `Always` 요청
3. 위치 권한 이후 알림 권한 요청
4. 거절된 경우 설정 화면 이동 기능 제공
5. 앱 복귀 시 실제 OS 권한 상태 재조회

### Flutter 지도에서 마커가 표시되지 않거나 터치가 충돌하는 문제

#### 원인

iOS 네이티브 지도를 `PlatformView`로 연결하는 과정에서 Flutter의 스크롤·탭 제스처와 지도 제스처가 경쟁했습니다.

마커 갱신 시점이 지도 생성 시점보다 앞서는 경우에는 마커가 표시되지 않았습니다.

#### 해결

- 네이티브 지도 준비 완료 후 마커 전달
- 마커 상태 변경 시 명시적으로 네이티브 뷰 갱신
- PlatformView gesture recognizer 타입 통일
- 마커와 하단 시트의 선택 상태를 하나의 ViewModel에서 관리
- 연속 탭으로 인한 화면 중복 이동 방지

### 포그라운드 알림이 표시되지 않거나 문구가 중복되는 문제

#### 원인

FCM 포그라운드 메시지와 로컬 알림, 앱 내부 토스트가 동시에 같은 메시지를 처리하면서 알림이 누락되거나 중복 표시됐습니다.

#### 해결

앱 상태에 따라 알림 표시 책임을 분리했습니다.

- 포그라운드: 앱 내부 토스트
- 백그라운드 및 종료 상태: 시스템 푸시
- 알림 탭 액션: 별도 Bridge를 통해 앱 라우팅으로 전달

메시지 파싱과 UI 표시 로직도 분리하여 같은 이벤트가 두 번 렌더링되지 않도록 했습니다.

### 시간 조건이 자정을 넘을 때 잘못된 범위가 생성되는 문제

#### 원인

단일 시각에 앞뒤 1시간을 적용하면 `00:30` 또는 `23:30` 같은 입력이 전날이나 다음 날로 넘어가는 문제가 있었습니다.

#### 해결

현재 데이터 모델에서는 자정을 넘어가는 범위를 만들지 않고 다음과 같이 절단했습니다.

- 시작 시간이 자정 이전이면 `00:00`
- 종료 시간이 자정 이후이면 `23:59`

관련 알림 조건을 단위 테스트로 검증했습니다.

### Elasticsearch 버전 불일치로 검색 서버 연결에 실패한 문제

#### 원인

Spring Data Elasticsearch가 기대하는 클라이언트 버전과 Docker Elasticsearch 버전이 일치하지 않아 연결 및 매핑 생성 과정에서 오류가 발생했습니다.

#### 해결

- Spring Boot 의존성과 호환되는 Elasticsearch 버전으로 통일
- Docker Compose 이미지 버전 고정
- 인덱스 settings와 mappings를 애플리케이션 리소스로 관리
- 애플리케이션 시작 시 인덱스 존재 여부 검사
- 필요한 경우 검색 인덱스 자동 초기화

### Redis 장애가 장소 검색 전체 장애로 전파되는 문제

#### 원인

캐시는 성능 최적화를 위한 보조 시스템이지만 Redis 조회 예외가 그대로 전파되어 장소 검색 API까지 실패했습니다.

#### 해결

Redis의 조회·저장·분산 락 처리에 각각 예외 처리를 적용했습니다.

Redis를 사용할 수 없을 때는 외부 장소 API를 직접 호출하는 fail-soft 전략을 적용했으며, 손상된 JSON 캐시는 삭제한 뒤 새 데이터를 적재하도록 구성했습니다.
